Looking after the Selah server ({{SERVER}}): starting and stopping it, updates, backups, and what to do when something's wrong. Every heading folds.

This guide opens read-only, and Selah updates it with each new version. The commands go in a terminal on the server (SSH in as the account Selah runs under). The full rebuild runbook is DISASTER-RECOVERY.md in the app folder.

The selah command

One command for the everyday jobs. It works from any folder.

Command

What it does

selah check

Checks everything Selah needs: running, answering, starts at boot, the notes disk, backups. Start here when something seems wrong.

selah status

Whether the service is running, and since when.

selah stop

Stops Selah, for maintenance. It still starts again at the next boot.

selah start

Starts it and waits until it answers.

selah restart

Stop and start, e.g. after changing a setting in the service or a certificate.

selah logs

The last 60 lines of its log. selah logs 300 shows more; selah logs -f follows it live (Ctrl+C to stop).

selah update

Gets the latest code from GitHub, builds it and restarts. Notes aren't touched.

selah backup

Backs up now: a local copy, then the encrypted off-site copy if it's set up (both happen every night anyway).

selah version

The version installed.

If selah isn't found (a rebuilt server), run bash scripts/install-service.sh in the app folder; it installs the service and the command.

Starting at boot

  • Selah runs as a systemd user service called note-app. It's enabled (starts at boot) and the account has linger on (runs without anyone logged in). Nothing needs doing after a reboot.

  • To confirm after a reboot: selah check. Every line should have a ✓, and "server up since" shows when the machine started.

  • If it ever crashes, systemd restarts it after 3 seconds.

  • If linger has been turned off, Selah stops when you log out. Turn it back on with sudo loginctl enable-linger $USER (it needs sudo, so run it yourself).

  • If the notes disk doesn't mount at boot, Selah refuses to start rather than open an empty notebook; selah check says so. See "The notes disk".

Maintenance

Stopping for maintenance

  1. selah backup, so there's a fresh copy.

  2. Finish what you're typing (on every device), then selah stop. Until it's back, Selah's pages and the Windows app can't reach the server.

  3. Do the work (disk, operating system, moving files).

  4. selah start, then selah check.

Operating system updates

  • On Debian/Ubuntu: sudo apt update && sudo apt upgrade, then reboot if it asks (sudo reboot). Selah starts by itself; check with selah check.

  • Node.js is separate from the system: it lives in ~/.local/node and the service uses ~/.local/node/current/bin/node.

Updating Selah

  • Releases are usually built and restarted for you. To bring in code pushed to GitHub from elsewhere: selah update.

  • It stops if the app folder has uncommitted changes, and only reinstalls packages when they changed.

  • After an update, open pages show a banner: click Reload. The Windows app updates itself separately (tray menu → Check for updates).

Backups

  • Every night at about 03:15 a backup of the database and every attachment goes to {{DATA}}/backups on the system disk (the newest 14 are kept). selah backup makes one now (with the off-site copy).

  • Off-site: after the nightly backup, an encrypted copy goes to OneDrive (Settings → Data & backup → Off-site backup). Its health is on the dashboard's Backups widget. Keep the backup passphrase off this server.

  • Test the passphrase every few months (the widget reminds you).

Restoring from a local backup

For a damaged database or a big mistake, on this server:

selah stop
cd {{APP}}
mkdir /tmp/restore && tar xzf {{DATA}}/backups/note-app-YYYY-MM-DD-HHMM.tar.gz -C /tmp/restore
cp /tmp/restore/notes.db {{NOTES}}/notes.db && rm -f {{NOTES}}/notes.db-wal {{NOTES}}/notes.db-shm
rsync -a /tmp/restore/files/ {{NOTES}}/files/
selah start
rm -rf /tmp/restore

For a single note, you rarely need this: try the note's Version history (⋯ menu) or the Trash first.

If the server is lost

Follow DISASTER-RECOVERY.md (in the app folder and on GitHub): a new server, the code from GitHub, then npm run restore brings everything back from OneDrive. Rehearse it now and then; the runbook's last section shows how without touching the real app.

The notes disk

  • The database and attachments live on their own disk, mounted at {{NOTES}}. Backups and certificates stay on the system disk, so losing one disk doesn't lose both.

  • selah check shows whether it's mounted and how much space is free. Settings → Data & backup → Storage shows what uses the space.

  • If it isn't mounted after a boot: sudo mount -a, then selah start. If it still won't mount, check the disk with your hypervisor or sudo dmesg | tail.

When something's wrong

What you see

What to do

The page won't load, or the app says it can't reach the server

selah check. If it isn't running: selah start. If it won't start: selah logs shows why.

"Not secure" in the browser

That device doesn't trust Selah's certificate yet: Settings → Security → Trust this device. Use the server's name, not a new IP address.

Forgot the password

In the app folder: npm run set-password (12 characters or more). Every device is signed out.

Lost the phone with the authenticator app, and the recovery codes

In the app folder: npm run reset-two-step. Sign in with the password, then turn two-step sign-in on again in Settings → Security.

"Too many failed attempts"

Wait 15 minutes. Settings → Security → Activity (from another signed-in device) shows the addresses.

Notes disk not mounted

See "The notes disk".

Disk full

df -h. Old local backups are pruned to 14; Settings → Data & backup → Storage and the Attachments page show large files.

A change didn't appear after an update

Click Reload on the update banner, or refresh the page. In the Windows app: tray → Quit, then open it again.

Reminders don't arrive

Settings → General → Notifications → Send a test. Focus mode skips reminders.

Security settings on the server

Set these in the service's environment (systemctl --user edit note-app) only when the setup changes, for example when Selah moves behind a proxy with a public certificate:

Setting

What it does

NOTEAPP_HSTS=1

Tells browsers to use HTTPS only, for a year. Only with a publicly trusted certificate: with the home certificate, a device that doesn't trust it yet couldn't click through the warning.

NOTEAPP_TRUST_PROXY

true, a number of proxies, or their addresses: behind a reverse proxy, use the visitor's address from it (for the devices list, the log and the failed-attempt limits).

NOTEAPP_FETCH_ALLOW

Host names (or host:port) on the home network Selah may fetch from, such as a WordPress site at home. Otherwise clipped pages, images, calendar feeds and WordPress are never fetched from private addresses.

NOTEAPP_RATE_LIMIT

Requests a minute from one address before it's slowed down (2400).

Hosting Selah for others (6.0)

Besides your own Selah, this server can host a Selah for each person you invite (a tenant), each at its own address with its own notes, sign-in and backups, looked after from the admin console. Your own Selah keeps running as it is.

How it fits together

  • The gateway (Caddy, the selah-gateway service) holds the certificate and sends admin.<domain> to the admin console and <name>.<domain> to that tenant. The console answers only from the allowed addresses (until you list some: home and private networks at home, only the server itself on a cloud server).

  • The admin console (the selah-admin service) has its own password and requires two-step sign-in. It creates tenants, sends setup links, checks every tenant each minute (restarting one that stopped), copies their security logs, runs the nightly host backup and moves tenants to new versions.

  • Each tenant runs as its own service (selah-tenant-<name>; on a cloud server, a Docker container) with limits on storage, upload size, memory, processor and job time. Tenants can't reach each other or the console.

  • You never know a tenant's password: their setup link has them choose it and set up two-step sign-in. A reset link handles a forgotten password or a lost phone. The console has no way to read anyone's notes.

Setting it up at home

cd {{APP}}
npm run install-caddy
npm run admin -- init --domain selah.example.lan
npm run admin -- set-password
npm run admin -- install

The domain needs a wildcard DNS entry (*.selah.example.lan) pointing at this server. At home the gateway listens on port 9443 with a wildcard certificate from the home CA, so devices that trust Selah already trust it. Then open https://admin.<domain>:9443, sign in and turn on two-step sign-in.

A cloud server (6.0.1)

On a rented server (a VPS with Ubuntu 24.04 or newer) tenants run as Docker containers, the gateway listens on port 443, and the certificate is a Let's Encrypt wildcard that Caddy gets and renews itself, proving the domain through Cloudflare DNS.

Once, when the server is new (as the ubuntu user, with your SSH key added): SSH keys only (a file in /etc/ssh/sshd_config.d/ with PasswordAuthentication no, PermitRootLogin no; check cloud-init's own file there doesn't turn passwords back on), the firewall on with only SSH (sudo ufw limit 22/tcp, sudo ufw enable), fail2ban, and automatic security updates. The firewall's limit refuses a sixth SSH connection within 30 seconds, so reuse one connection (SSH ControlMaster) for scripts.

DNS: in Cloudflare, an A record for * (or *.selah) pointing at the server, set to DNS only (grey cloud), and an API token from the Edit zone DNS template limited to the domain.

The code and the rest, from the home server's app folder:

bash scripts/cloud-push.sh <ssh host> --setup

That copies the code to ~/selah on the server and runs scripts/cloud-setup.sh: Docker (containers can't reach each other; logs capped), port 443 for the gateway, HTTPS through the firewall, Node.js, rclone, Caddy built with the Cloudflare module, and the build. Then on the server, in ~/selah:

npm run admin -- init --domain example.com --tls acme --runner docker --allow-ip <your home address>
npm run admin -- dns-token
npm run admin -- set-password
npm run admin -- install
npm run admin -- prepare-release

dns-token asks for the Cloudflare token, checks it with Cloudflare and keeps it only in the gateway's settings file (readable by this user alone). The certificate arrives within a minute of install; npm run admin -- cert shows it. The console answers only from the addresses you allow (with none listed, only from the server itself), so add your phone's or a new home address with npm run admin -- allow-ip add <address>.

Updating the cloud server: from the home server, bash scripts/cloud-push.sh <ssh host> sends the new code, builds it and restarts the console; then Prepare release and Update all in the console (or npm run admin -- prepare-release and npm run admin -- update on the server).

Moving your own Selah to the cloud

  1. On the home server: npm run cloud-export -- ~/selah-move/trial. It copies the database (safely, while Selah runs), attachments, the secrets key, shared captures and the Windows app downloads, with a checksum for every file. Nothing at home changes.

  2. Send it: rsync -a ~/selah-move/trial <ssh host>:imports/.

  3. On the cloud server: npm run admin -- import <name> --from ~/imports/trial. Every file is checked against the export before anything is made, and the counts (notes, notebooks, attachments, tags, tasks, events…) are compared once it runs. Sign in at https://<name>.<domain> with your usual password and authenticator.

  4. When you're happy with it, move for real: stop Selah at home (systemctl --user stop note-app note-app-backup.timer), export again with --with-offsite (which brings the OneDrive backup connection, so the cloud copy carries on backing up to the same folder), send it, and import with --replace. The trial's data goes to the trash for 7 days.

  5. Point things at the new address: Selah for Windows (tray → Server address…), the Edge clipper (download it again from Settings on the new address), and bookmarks or the installed app on your phone. Keep the home server's data until you're sure; systemctl --user start note-app brings it back.

The admin command

Command

What it does

npm run admin -- status

The console, the gateway, the certificate and every tenant.

npm run admin -- create <name>

A new tenant, with its setup link (the console's New tenant does the same).

npm run admin -- setup-link <name> [--reset]

A new one-time setup or reset link.

npm run admin -- allow-ip add <address>

Lets the console answer from that address. Use it if a changed address locks you out.

npm run admin -- reset-two-step

For the admin's own lost phone and recovery codes.

npm run admin -- cert

Issues the wildcard certificate again (the console warns three weeks before it expires). With Let's Encrypt, shows the certificate; the gateway renews it itself.

npm run admin -- dns-token

Saves a new Cloudflare API token for the gateway (asks for it, checks it, restarts the gateway). Use it when you roll the token.

npm run admin -- import <name> --from <folder> [--replace]

A home server's Selah (from npm run cloud-export) as a tenant, checked file by file and by counts.

npm run admin -- restore-file <name> <file>

Restores a tenant from a backup file they downloaded (asks for its passphrase); their data is moved aside first.

npm run admin -- prepare-release, update [<name>…]

The console's Prepare release and Update all, from the command line.

npm run admin -- suspend | resume | delete <name>

Pause a tenant, start it again, or delete it (its folder stays in the trash for 7 days).

npm run admin -- maintenance-stop

Stop Selah everywhere for server maintenance: the console, every tenant (each finishing what it's doing) and the gateway. A reboot, or maintenance-start, brings it all back. Every step: console → Docs → Maintenance Procedure.

Backups and restores

  • The host backup (console → Backups) copies every tenant every night (02:30 UTC unless you change it), encrypted, to up to four places at once: OneDrive, S3-compatible storage, WebDAV or any rclone remote, each with its own passphrase (Add a destination…). It keeps 30 days of snapshots and checks each tenant's backup weekly. Keep the passphrases off this server.

  • Tenants can add their own encrypted off-site backup too (Settings → Data & backup), to OneDrive, an S3-compatible bucket or a WebDAV server; each runs at its own time between 03:15 and 06:15 UTC. They can also download a backup file whenever they like (.selahbak, encrypted with a passphrase they choose, or a plain .tar.gz).

  • Restore… on a tenant: a test restore proves a snapshot can be restored without changing anything; restore over their Selah moves their current data aside (kept in their folder) and puts the snapshot in its place. Everyone signs in again afterwards.

  • Restore… → Notes & Notebooks: bring back single notes or whole notebooks into a tenant's running Selah, as copies, from a host-backup snapshot. You see notebook names and note titles only.

  • Restore… → From a Backup File: upload a tenant's downloaded backup and enter its passphrase. It's unpacked and checked (the passphrase, the encryption tag, the database and every attachment) while their Selah keeps running; only then does it stop, move their data aside and put the backup in its place. The same from the command line, for a big file copied to the server: npm run admin -- restore-file <name> <file>.

  • On a new server, set up the host backup with the same passphrase: tenants in the backup but not on the server are listed under In the backup, not on this server, each with Bring back.

Updates

  • Tenants run from a release, a copy of the code at one version. After selah update brings in a new version, open console → Updates and Prepare release, then Update all.

  • Tenants move one at a time: each is backed up, restarted on the new release and checked. If one doesn't come up it goes back to its old release, with its database as it was, and the update stops there. Roll back puts any tenant back on the release it had before.
